## Notes on these runs

### Why a failed COMMIT never reaches the application on macOS

Apple's NFS client, apple-oss-distributions/nfs at commit 93733ffccece4daee73bf6306b291d1ae69130c0:

- `kext/nfs_vnops.c`, `nfs3_commit_rpc()`: line 7493 (`error = status;`) turns a COMMIT's NFS error into the function's error, and line 7502 (`error = NFSERR_STALEWRITEVERF;`) does the same for a changed write verifier.
- `kext/nfs_bio.c`, `nfs_flushcommits()` (from line 3519), which `fsync(2)` reaches through `nfs_flush()`:
  - the commit result goes to `retv` (lines 3685 and 3691);
  - when `retv` is set (lines 3712–3713, "move back to dirty list"), the buffers go back to the dirty list;
  - the function returns `error` (line 3759), which the commit never set.
- `kext/nfs_bio.c`, `nfs_buf_write_finish()`: line 2962 (`nfs_buf_pgs_bit_and(&bp->nb_dirty, ...)`) already cleared the pages' dirty bits when the UNSTABLE WRITE succeeded. The pages put back after a failed commit are therefore never written again.
- Only the single-buffer path, `nfs_buf_write()`, sets `NB_ERROR` on a failed commit.

So an `fsync` whose COMMIT fails, whether answered with an error or with a changed verifier, returns 0. The trace build confirmed it each time: COMMIT answered `NFS3ERR_IO`, the application's `fsync` returned within milliseconds, and the kernel sent no further WRITE.

### What was measured

- **Revocation during a 64 KiB write+fsync loop:** the last acknowledged record was missing in 6 of 9 rounds.
- **SIGKILL, then the dead mount forced off** (by `mountable unmount`, or by macOS's own dead-mount handling at about 36 s): a pending `fsync` returned 0, and its record was missing, in 4 of 8 rounds.
- **A COMMIT answered OK with a new verifier** (prototype): `fsync` still returned 0 at once, with no rewrite.
- **Write-through prototype** (every WRITE answered FILE_SYNC after persisting it): 4/4 revocation and 4/4 SIGKILL rounds lost nothing, and the kernel sent no COMMIT.
- **Throughput for 64 MiB of `dd`** in production, UNSTABLE+COMMIT against write-through:

  | `dd` block size | UNSTABLE+COMMIT | write-through |
  |---|---|---|
  | 1 MiB | 9.8 MiB/s (65 WRITEs, 3 COMMITs) | 6.8 MiB/s (65 WRITEs, 0 COMMITs) |
  | 32 KiB | 9.3 MiB/s (66 WRITEs, 5 COMMITs) | 7.0 MiB/s (66 WRITEs, 0 COMMITs) |

- **Limits with UNSTABLE+COMMIT:** under a spending cap at the reservation, 256 MiB was written, `fsync` and `close` returned OK, and 0 bytes were stored. Past the byte quota, 192 MiB was written, `fsync` and `close` returned OK, and 0 bytes were stored. When a refusal did surface, it was EIO, not EDQUOT.

### Busy unmount (L6)

SIGINT and `mountable unmount` find the clean unmount refused while the mount is busy (for example a Terminal's working directory inside it). They force the mount off at once, with the warning that uncommitted writes may be lost, as on Linux. The 30-second budget only bounds a clean stop that hangs. Under UNSTABLE+COMMIT, that forced path also dropped the writes the adapter had accepted UNSTABLE but not yet flushed. With write-through, a WRITE is answered only once it is persisted, so nothing acknowledged remains to drop; this is re-verified with the write-through build.

### Production's quota floors

Production's API still refuses an `entry_quota` below 10,000 and a `byte_quota` below 1 GiB (422, `greater_than_equal`), although D44 removed the floors. Li4 therefore runs on the dev stack.

## 0.6.1 work found by these runs

- **Files rewritten in place reach the chunk cap.** With no merge on an NFS WRITE, every partial overwrite keeps a chunk. A file rewritten in place, such as a SQLite database, gets "file too large" after about 9,999 rewritten ranges. v0.6.0 publishes this as a limit, and a test pins it (`TestNFSWriteInPlaceRewritesReachTheChunkCap`). The 0.6.1 fix re-uploads a WRITE's chunk window, its visible data plus the new bytes, as one chunk before `Begin`, within the preparation budget.
- **Killed mounts' cache directories** (#24) moves to 0.6.1, redesigned: one per-root lock, and pruning only this host's local directories. D1 records the leftover directory again until then.
